Guide

Status: draft, in demo mode. The boat-file format, its checker (rigframe validate), the example boats, the 3D viewer and the GitHub workflow are here. The analysis engine is still being moved out of the notebooks it was developed in. Until it lands, rigframe run checks your file and writes a report of its estimates, marked DEMO. For the four example boats it also replays the notebook studies' stored results in the viewer; those don't change if you edit the file. pipx install rigframe will work once it's released. For the full analysis today, use the notebooks.

This is an engineering estimate, not a rig survey. It assumes the rig is in good condition, and it knows nothing about corrosion, fatigue, cracked swages or worn chainplates. Have a rigger inspect the rig. The report says which numbers are estimates; treat them that way.

Four ways to get a report

What you need Who sees your boat What you get today
A notebook, in Colab or on your computer A web browser (Colab), or Python 3.12 Only you The full analysis and the 11 × 17 report
A pull request to this repository A free GitHub account and a web browser Everyone: this repository is public Demo report and 3D viewer
Your own private copy A free GitHub account Only you, and anyone you invite Demo report and 3D viewer
Your own computer, with the package Python 3.12 or later Only you Demo report and 3D viewer

The last three start from a boat file. The notebooks are separate: each holds one boat's whole analysis, and you edit its inputs in one cell.

The notebooks: the full analysis today

notebooks/ holds the three studies the method was built and checked on. Each runs on its own: it needs neither GitHub Actions nor the rigframe package. Each one tunes the rig at the dock, sails it through every load case, checks mast buckling, and cross-checks the main cases in a second solver. It ends in a table of 30 to 53 PASS/FAIL checks.

Notebook Rig Open
beneteau-oceanis-440-1994 Masthead sloop, two sets of swept spreaders, discontinuous shrouds, four lowers, split backstay, in-mast furler
island-packet-40-1996 Masthead cutter: one spreader set, fore and aft lowers, staysail stay, twin backstay
morgan-462-ketch Masthead ketch, two masts, run with a triatic and with split backstays

In Google Colab: click a badge, then Runtime → Run all.

  • The setup cell fetches this repository for its data.
  • The install cell adds what Colab lacks, in about a minute. It holds Colab's own numpy, SciPy, pandas and Matplotlib where they are, because swapping a package the session has already loaded breaks its imports. If it can't avoid that, it stops and asks you to restart the session (Runtime → Restart session) and run all again.
  • The run takes a few minutes more. To keep the results, download the output folder from Colab's file pane.

Colab runs a newer Python than 3.12. If OpenSees won't load there, the cross-check reports SKIP and the rest runs.

On your computer, with Python 3.12, from the notebooks/ folder:

python -m venv .venv

Activate it (.venv\Scripts\activate on Windows, source .venv/bin/activate elsewhere), then:

pip install -r requirements.txt

Open the notebook in Jupyter or VS Code and run it. Python 3.12 matters only for the OpenSees cross-check: its Windows build needs exactly 3.12. Without OpenSees those checks report SKIP and everything else runs.

To study your own boat, pick the notebook nearest your rig and edit its RigParams cell. Every input is there, and the ones marked # PLACEHOLDER are estimates.

What a run writes, in notebooks/output/<notebook>/:

  • REPORT.md, every load case item by item, with its figures in assets/;
  • viewer-3d.html, the standalone 3D viewer.

To turn the report into an 11 × 17 in PDF:

python tools/md_to_tabloid_pdf.py notebooks/output/island-packet-40-1996/REPORT.md

LaTeX typesets it, in CMU Serif (Computer Modern) with proper math. That needs pandoc, a TeX distribution with XeLaTeX and the CMU fonts, and rsvg-convert for the figures:

  • Windows: MiKTeX installs the fonts on demand.
  • Ubuntu: sudo apt install pandoc texlive-xetex texlive-latex-extra texlive-science lmodern fonts-cmu librsvg2-bin.

Without LaTeX, add --engine chromium to print it with a browser instead (pip install playwright, then playwright install chromium once).

Sample reports. The sample-reports release has the finished PDFs for all three boats, so you can see what you'll get before running anything:

  • *-report.pdf, written by the notebooks;
  • *-companion.pdf, the method behind each study: every load case with free-body diagrams, how each sail load is applied, the terms, and the textbook equations by number and page.

GitHub Actions rebuilds them whenever a notebook, a companion or the PDF tool changes: it runs the three notebooks, typesets the PDFs and replaces them on the release. The companions were written by hand for these three boats; their source is in docs/companions/.

Step 1: Make your boat file

The boat file says what your rig is and where each number came from. Getting the numbers together is the hard part, so there are two ways in.

The easy way: have an AI assistant draft it

prompts/make-boat-yaml.md is a prompt you paste into an AI assistant with web search turned on (Claude, ChatGPT, Gemini or similar). It reads this repository's rules, looks up your boat's published data, asks you only what it can't find, and hands back:

  • the file name to use;
  • the finished YAML;
  • the sources it used;
  • a list of what to measure, most important first.

Attach photos when it asks: the rig from the side and from astern, each chainplate, the label at the mast foot. They settle questions no website answers.

By hand

Copy docs/boat-template.yaml, or the example nearest your rig:

Your rig Start from
Sloop, one set of spreaders docs/boat-template.yaml
Sloop, two or more sets boats/beneteau-oceanis-440-1994.yaml
Cutter boats/island-packet-40-1996.yaml
Ketch or yawl boats/morgan-462-ketch-triatic.yaml or …-split-backstays.yaml

docs/boat-yaml.md explains every field, how to measure it and where to look it up.

What a value looks like

I: {value: 53.15 ft, basis: published, ref: gob}   # with its source
gooseneck_z: 1.75 m                                 # bare: counts as an estimate

Every number has a unit, and you keep the unit your source used. basis is measured, maker, published or estimate. A file full of estimates still runs; the report just says so.

Name the file

<builder>-<model>-<year>.yaml, lowercase, with hyphens: catalina-36-1989.yaml. To compare two arrangements of the same boat, make two files and add the difference to the name: morgan-462-ketch-triatic.yaml and morgan-462-ketch-split-backstays.yaml.

Leave out anything personal

No owner's name, boat name, hull identification number, sail number or home port. A pull request here is public. If you'd rather keep the boat itself private, see Keeping your boat private.

Step 2: Open a pull request with your file

A pull request is how you hand a file to a GitHub repository you don't own. You do it all in the browser. GitHub makes your own copy of the repository (a fork) along the way, and you don't have to manage it.

Before you start: sign in to github.com. A free account is enough.

2.1 Add the file

  1. Go to the boats folder of this repository.
  2. Click Add file (top right, above the file list), then either:
    • Upload files, and drag your .yaml file onto the page; or
    • Create new file, type the file name into the box above the editor (the boats/ part is already there), and paste your YAML into the editor.
  3. GitHub says you need your own copy to propose a change. Click Fork this repository. This happens only the first time.

2.2 Propose the change

  1. Click Commit changes… (or Propose changes on the upload page).
  2. In the box that opens, write a title such as Add Catalina 36 (1989). The description can stay empty.
  3. Click Propose changes. GitHub shows a page titled Comparing changes, with your file in green.
  4. Click Create pull request.

2.3 Fill in the pull request

  1. The description box holds a short checklist. Tick what applies: where most of the numbers came from, and that the file has nothing personal in it.
  2. Click Create pull request again. That's it: your pull request is open.

2.4 Watch the check

At the bottom of the pull request a check called Boat report appears.

  • "Waiting for approval" or "1 workflow awaiting approval": GitHub holds the first pull request from a new contributor until a maintainer lets it run. You don't need to do anything. It usually happens within a day.
  • Yellow dot: it's running. A full run takes a few minutes.
  • Red ✗: something in the file needs fixing. Go to 2.5.
  • Green ✓: the report is ready. Go to 2.6.

2.5 If the check fails

  1. Click Details next to the red ✗. The log opens at the step that failed.

  2. Under Check the boat files, the checker lists each problem in plain words, usually with the line to fix:

    FAIL  boats/catalina-36-1989.yaml
      - sail_plan.I (line 30): '45 feet' needs a number, a space, then one of: mm, cm, m, in, ft.
      - masts.0.shrouds.cap (line 70): Additional properties are not allowed ('pretention' was
        unexpected) Check the spelling against docs/boat-yaml.md.

  3. Fix it in the browser: in your pull request click Files changed, then the ⋯ menu at the right of your file's header, then Edit file. Make the change, then click Commit changes… and Commit changes. Leave it on the same branch; GitHub offers that by default.

  4. The check runs again by itself. Repeat until it's green.

If you're stuck, write a comment on the pull request and paste the error. Someone will help.

2.6 Open the 3D viewer and the report

There are two ways in. The first needs nothing but a click.

Online, from the pull request. A minute or two after the check goes green, a comment titled Rig report preview appears on your pull request, posted by github-actions.

  1. Click Open the 3D viewer. It opens in your browser, on a phone too.
  2. Pick a load case with the buttons along the top. Drag to turn the rig, scroll or pinch to zoom, and hover over (or tap) any wire, mast panel or spreader to see its load. Step 3 explains the colours.
  3. Report and PDF, in the same comment, open the full report.

The links work for anyone you send them to. If one shows "404", wait a minute: GitHub Pages takes a moment to publish. The preview follows every change you push, and it's removed when the pull request closes, so download a copy if you want to keep it.

As a download, to keep.

  1. Click Details next to the green ✓, then Summary at the top left of the page that opens. The summary shows the headline: the governing wire and its safety factor in each load case, the mast's peak stress, the lowest buckling factor, and how many inputs are still estimates.
  2. Scroll to the bottom, to Artifacts, and click rig-report-. You get a zip file. GitHub keeps it for 90 days.
  3. Unzip it and double-click viewer.html. It opens in your browser and works without internet, so you can show it to someone on the dock. The zip also holds REPORT.html, REPORT.pdf, the figures, viewer.json (the results as data) and a copy of your boat file.

You can share the zip, viewer.html on its own, or just the PDF, with anyone.

2.7 What happens next

  • You only wanted the report: close the pull request (the Close pull request button at the bottom). Your report is already downloaded.
  • You'd like the boat to stay here as an example for others: leave it open and say so in a comment. The maintainer may ask a question or two, then merge it. A merged boat gets a permanent page: its 3D viewer at https://rigframe.github.io/rigframe/boats/<file name>/viewer.html, and its report beside it. The front page lists every published boat. The pages update whenever rigframe improves.
  • You measured more later: edit the file in your pull request (step 12) and the report runs again. If the pull request is already closed or merged, open a new one the same way.

Step 3: Read the report

The report opens with the things to check first:

  1. Estimates. Every input still marked estimate, most influential first. Until those are measured, the numbers that depend on them are estimates too.
  2. Rigging list. Every wire with its size, length, breaking load, dock tension and highest load. The lengths run pin to pin on the model's geometry; they aren't cut lengths.
  3. All cases at a glance. One row per load case: the governing wire and its safety factor, the mast's peak stress and utilisation, the buckling factor.

Then each load case in full, and the method: what each case means, how the sail loads are applied, the textbook equations behind it, and the cross-check against a second solver.

The 3D viewer

  • Colour is utilisation, on one scale for everything: a wire's tension as a share of its breaking load, and a spar's peak stress as a share of the aluminium's yield. Pale is lightly loaded; dark brown is at or past 50%. A dotted grey wire is slack.
  • The cards above the view give the case's peak mast stress, the most-loaded wire and its safety factor, the peak spreader stress, and how far each masthead moves.
  • The shape is exaggerated. The Displacement × slider sets by how much (8 times by default). Tick Undeformed to see the rig at rest behind it.
  • Hover shows each member's numbers: tension, safety factor and wire stress for a wire; peak stress, axial load and bending moments for a spar. The tooltip on each case button names the solver that ran it.

Safety factor

Safety factor here is the wire's minimum breaking load over its tension in that case. It has to cover everything the model leaves out: gusts beyond the case, wave slamming, fatigue, worn fittings. Shigley's Mechanical Engineering Design asks for at least 3.5 on guy wires (Table 17-25). The report explains what each case's factor means.

Keeping your boat private

If you'd rather nobody else saw your boat file or report, run rigframe in your own private copy of the repository.

  1. On this repository's page, click Use this template (top right), then Create a new repository.
  2. Give it a name, choose Private, and click Create repository.
  3. In your new repository, add your boat file to boats/ exactly as in 2.1, but commit it straight to main (there's nothing to fork).
  4. Open the Actions tab. The Boat report run appears within a minute. When it's green, open it and download the report from Artifacts, as in 2.6. viewer.html in the zip is the full 3D viewer and needs no internet.

GitHub's free plan includes Actions minutes for private repositories, and one report takes a few of them. Private repositories can't publish GitHub Pages on the free plan, so there's no online preview and the report comes only as a download.

Running it on your own computer

pipx install rigframe

rigframe validate boats/my-boat.yaml

rigframe run boats/my-boat.yaml --out reports/

validate checks the file in under a second. run writes the report folder, with viewer.html in it. The viewer carries its own copy of plotly.js (about 5 MB), so it opens offline. To rebuild it as a 50 kB file that fetches plotly.js from the internet instead, for a web page or an email, run rigframe viewer reports/my-boat/viewer.json viewer.html --cdn. The OpenSees cross-check needs the optional extra (pipx install "rigframe[opensees]"); see Licences. Without it, the report says the cross-check was skipped.

In VS Code with the YAML extension, the first line of every boat file points at schema/boat.schema.json, so you get completion and error marks as you type.

How it works

  • The frame. The mast and spreaders are beam elements and every wire is a tension-only bar, in Pynite. Both masts of a ketch or yawl are in one model.
  • The dock tune. Each turnbuckle's shortening is solved by Newton iteration so that every wire reaches its target tension at once. The forestay is reached the way a rigger reaches it, through the backstay (or, on a ketch with a triatic, the mizzen backstays).
  • Sailing. One sail pressure, chosen so the heeling moment about the deck equals the righting moment at 30° heel (times the case's factor), acts on the main's and the headsail's areas. The main's force runs along the mast between the boom and the head, largest at the boom. A third of the headsail's force goes to the masthead and the rest straight to the stem, unless the case spreads it along the stay. P-Delta analysis includes the mast's bow.
  • Stays that sag. With the headsail's load spread along its stay, the stay's tension comes from its own stretch. That needs a large-displacement solver, so those cases run in OpenSees with corotational elements and are checked against the cable equation.
  • Buckling comes from the stiffness and geometric-stiffness matrices; open-section torsional-flexural buckling is checked by hand.
  • Cross-check. The dock tune and the main load cases are re-run in OpenSees, and the report prints the differences. Pynite's linear P-Delta leaves out the shortening of a bowed mast, which puts its forestay 1–2% above the large-displacement answer; the report flags it.
  • Checks. Every run ends in a table of PASS/FAIL checks: equilibrium, the cross-check, the cable equation, Euler buckling of each panel. A failed check stops the report from calling itself finished.

The method was built and validated in three studies: a masthead sloop with discontinuous shrouds and four lowers, a masthead cutter, and a masthead ketch with both triatic and split-backstay arrangements. Those three are the example boats.

Adding to rigframe

  • A new boat is a pull request with a YAML file, as above.
  • A new load case is a function registered in rigframe/loads.py. It takes the boat and returns forces on nodes; the rest of the run picks it up.
  • A new rig layout (running backstays, a fractional rig's diamonds, a bowsprit with a bobstay) means teaching rigframe/geometry.py a new kind of wire, adding it to the schema, and adding an example boat that uses it. Open an issue first.
  • Every change has to keep the example boats' numbers. pytest compares each run with stored results.
